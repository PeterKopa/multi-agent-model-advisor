# Integrations

Reviewed requirements for [issue #1](https://github.com/PeterKopa/multi-agent-model-advisor/issues/1). Confirmed decisions are normative; open design checks are not verified capabilities.

## Assisted provider discovery and user-approved model selection

- Provide an explicit discovery/refresh action for selected providers. Prefer official structured model catalogs, APIs or supported local CLI inventory commands where available; optionally use the configured LLM CLI to assist with discovering public provider information, interpreting unstructured documentation, mapping model identifiers and proposing a shortlist against the user's filters.
- Treat discovered offerings and LLM suggestions as untrusted candidate data. Require source references, retrieval timestamps and explicit unknown values for unavailable metadata; never invent model availability, pricing, ZDR status or geographic guarantees. Validate structured output against the local schema and do not allow external content to change policy or execute commands.
- Separate discovery, deterministic local policy evaluation, and user approval. Present eligible, excluded and unresolved offerings with reasons, provenance and metadata freshness. Allow the user to add/remove candidates, correct metadata with provenance, adjust editable filters, or manually enter offerings. Mandatory policies cannot be bypassed by confirming a shortlist or by unverified AI suggestions.
- Persist the approved candidate selection locally with the project (or reusable global defaults where appropriate). On refresh, show added, removed and changed offerings before replacing the approved selection; retain user overrides and mark stale evidence. Keep discovery optional: manual catalog import and local scoring must work without the LLM.
- Discovery of public provider data should not require sending agent definitions, private repository content or confidential organization policies to an external LLM. Any external request must follow the configured privacy/geographic restrictions and explicit approval; disclose the data to be sent. Do not assume a chosen CLI has internet access or provider discovery capabilities.

## Ollama Cloud integration (MVP)

- Scope revision after the requirements review: focus the first MVP on hosted/cloud models. Support explicit refresh of the current public Ollama Cloud model catalog and discovery of configured cloud access routes through supported CLI integrations. Reuse existing Ollama allowances where supported, without requiring a new paid API key or silently switching billing routes.
- Distinguish public catalog entries from account-specific configured availability; public listing is not proof of subscription inclusion, remaining quota, permission or successful inference. Preserve exact route identities and supported model/version mappings.
- Display local-model support as "Coming soon" (localized German: "Demnächst verfügbar"). Do not implement local inference, local inventory discovery, downloadable-model discovery, quantization-specific evaluation or hardware compatibility checks in the MVP. If CLI discovery exposes a locally executed model, do not include it as an eligible hosted candidate; identify unresolved execution type explicitly and do not assume it is hosted or free.
- The Advisor itself, its scoring, project storage and offline/manual workflows remain local-first. Deferring locally executed LLMs does not change these requirements.

### Future scope: locally executed models (not an MVP requirement)

Retain the following requirements as design input for a later local-model feature, rather than implementing them in the initial release:

- Discover installed local models through the configured Ollama instance using its supported local inventory CLI/API. Allow an optional, separate discovery of downloadable models from the public catalog. Clearly distinguish installed, downloadable, cloud-backed and unknown execution types; do not assume an installed model identifier guarantees local inference.
- Record exact model identifiers, tags/digests, quantization, model size, available capabilities and context configuration when exposed. Map benchmark results to the appropriate model/version and flag quantization or configuration mismatches; do not present cloud benchmark results as measured local performance.
- Optionally collect local hardware information (RAM/VRAM, accelerator and available storage) with user consent and provide advisory compatibility estimates, distinguishing measured values from estimates and unknowns. Hardware details remain local by default.
- Apply the same deterministic eligibility filters and user confirmation workflow as for hosted offerings. Represent local execution separately from hosted ZDR claims, and local compute costs separately from free hosted offers. Verify execution/routing properties where possible; flag unknowns.
- Allow refresh of the local inventory, show changes before updating the approved selection, and preserve manual overrides. Support manual model entries and offline operation without the LLM assistant. Never automatically download, delete, run or benchmark models as a side effect of discovery; those actions require separate explicit user requests.

## CLI-based auto-discovery of available models

- Offer an optional auto-discovery action using installed and configured AI CLI clients. Target OpenCode v2 for the initial integration, using its supported model inventory interface (e.g. `opencode models`, subject to compatibility verification). Detect the installed version and supported capabilities; verify exact command, configuration format and prompt-only execution behavior before implementation. Include GitHub Copilot CLI as the second MVP coding-CLI adapter. Validate its current supported inventory, native model selection, configuration import, prompt-only execution and usage-reporting capabilities using official interfaces; use manual alternatives for unsupported capabilities. Defer Oh My Pi and further coding CLI clients to future stories. Keep model inventory adapters independent of LLM analysis adapters; the selected analysis CLI need not be the only discovery source.
- Run inventory discovery explicitly in the user-selected configuration/project context, respecting network permissions and existing CLI authentication. Do not retrieve/export credentials, invoke inference, or change client settings as part of inventory discovery. Handle unsupported versions, unavailable clients, errors and incomplete results with a manual import/selection fallback.
- Distinguish public catalog availability, models reported by the user's configured CLI, and the user's approved candidate selection. A reported model is evidence of configured availability, not proof of remaining quota, successful invocation, pricing or permission for a particular task.
- Preserve exact provider/model identifiers and discovery provenance, deduplicate overlapping entries without merging distinct offerings, apply selected filters locally, and present a selectable list. The developer may select/deselect models individually or in bulk, add manual entries, and confirm unresolved metadata for comparison using the existing conditional-inclusion workflow.
- Persist the approved selection per project. Refresh on explicit request, show additions/removals/changes, and never automatically approve new models or silently replace user selections. No inference calls are needed for the inventory itself.

## Configured CLI backends and custom provider identifiers

- Treat each discovered CLI inventory entry as an access route through a specific client, configuration context, configured backend/provider identifier, and exact backend model identifier. Support built-in and arbitrary user-defined backend IDs; do not assume a fixed list of provider names or infer the actual provider, tariff, endpoint, locality, or authentication method from a custom identifier.
- Preserve complete native model references, including nested namespace paths, version tags, suffixes and aliases. For OpenCode's provider/model references, separate the first provider separator from the remaining model ID, retaining the original full reference. Other adapters must use their own native identifier semantics.
- Group the selection UI by CLI and configured backend, with search and individual/backend-wide selection. Allow multiple backends for the same service, custom gateways and proxies, and multiple discovery sources for one project. Allow the user to identify or correct the underlying service and offering where not known; keep unresolved mappings explicit.
- Keep route identity, underlying service/endpoint and canonical benchmark model identity distinct. Never deduplicate different configured routes based on similar names alone. Map routes to shared benchmark evidence only when model/version/configuration matching is sufficiently supported; preserve separate pricing, routing and other filter metadata. Treat dynamic aliases/automatic routers as unresolved model identities unless their actual target is known.
- Persist backend-specific selections and mapping overrides locally; refresh using the corresponding configuration context and preserve user selections. Never collect credentials or transmit private configuration or inventory data to an external LLM automatically. Use public or non-secret metadata for optional enrichment, subject to existing consent rules.

## OpenRouter authenticated benchmark-data adapter

The official benchmark endpoint is documented at https://openrouter.ai/docs/api/api-reference/benchmarks/get-benchmarks (GET /api/v1/benchmarks; bearer authentication). Verify actual response fields and data usage terms in #4. A user-provided data credential is optional and scoped by the application to explicitly approved read-only OpenRouter catalog, benchmark and pricing requests. Use verified TLS and the official API origin; do not forward authorization on cross-origin redirects. Keep it separate from existing CLI authentication. Do not invoke inference, assume that the provider issues a read-only-scoped key, or create a new paid account automatically. Prefer a dedicated least-privilege/limited key where supported. Handle unauthorized, expired or rate-limited responses without disclosing credentials; retain manual/cached data fallback. The documentation does not establish actual credential-specific privileges, fees or runtime availability.

## OpenRouter transport security (confirmed requirement)

- Use Go standard-library net/http, crypto/tls and crypto/x509. Restrict the benchmark-data adapter to the official HTTPS origin https://openrouter.ai (port 443) and an explicit allowlist of supported read-only API endpoints. Validate the destination before attaching the credential. Do not allow user-configured arbitrary origins for this credential.
- Require TLS 1.2 or newer, prefer negotiation of TLS 1.3, and require standard certificate-chain, validity-period, server-authentication and hostname verification against the operating system's trusted roots. Never use InsecureSkipVerify, insecure HTTP fallback, an accept-invalid-certificate option, or TLS early data containing credentials. Reject connection and do not send authorization on failed TLS authentication.
- Disable automatic redirects for authenticated requests. Do not forward credentials to another host, subdomain, scheme or port. Default to direct connections for this adapter; any explicitly supported proxy mode must be separately configured and disclosed, retain full certificate verification, and never silently inherit or accept additional trust roots. If corporate TLS interception uses a root already trusted by the OS, normal certificate verification may accept it; disclose this residual risk. Do not claim interception detection from issuer names alone.
- Do not hardcode the current leaf certificate or its fingerprint as a trust requirement. Certificate rotation is normal. Optional SPKI pinning requires a separate threat-model and operational design with trustworthy pin distribution, backup pins and rotation/recovery; not a confirmed MVP feature.
- On security failures fail closed, report a redacted actionable error and allow offline/cached workflows. Never bypass certificate errors to make a connection test succeed. Reference: https://pkg.go.dev/crypto/tls, https://pkg.go.dev/crypto/x509, https://pkg.go.dev/net/http.
