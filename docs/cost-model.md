# Reference costs

Reviewed requirements for [issue #1](https://github.com/PeterKopa/multi-agent-model-advisor/issues/1). Confirmed decisions are normative; open design checks are not verified capabilities.

## Cost-efficiency objective (methodology to be defined)

- Confirmed question 7: use a uniform pay-per-token reference-cost approach for all hosted offerings in the MVP, including GitHub Copilot, Ollama Cloud and subscription-backed routes, regardless of actual billing arrangements. Use documented comparable public token prices or explicitly user-supplied reference prices with provenance and applicability labels; distinguish actual route prices from proxy/reference prices of other offerings. Missing comparable token rates remain unknown, not zero. Do not invent token-equivalent rates for subscriptions or request-based billing. Defer subscription-specific allowance accounting, preference and optimization beyond the MVP. Locally executed models are deferred (Coming soon); when supported later, treat them separately as local execution with optional user-supplied compute cost, not as hosted pay-per-token offerings or automatically free. Distinguish actual execution location from the backend label. Do not introduce a personal-versus-employer access classification. Existing project eligibility and privacy filters remain independent.
- The primary practical objective is to help developers obtain an adequately good result at the lowest reasonable total cost, rather than always recommend the strongest model or the lowest advertised token price.
- Keep the model-centric quality ranking independent of the default eligibility preference and separate from route-specific economics. Evaluate costs for a comparable task/workload and the actual eligible access route. Distinguish hosted token reference costs from actual charges and from local execution costs. Do not treat subscriptions as unlimited or unknown prices as zero.
- Define the cost-efficiency methodology as a separate architecture/scoring decision before implementing it. Candidate approaches include selecting the least-cost eligible route that meets a role-specific quality requirement and, when reliable task-level evidence exists, comparing total costs per successful outcome including retries, review and rework. Public benchmark scores are not calibrated probabilities of success on the user's tasks. Do not invent such probabilities, token consumption, subscription conversions or savings.
- The design must resolve how cost-aware recommendations relate to the unchanged quality ranking and the existing default-model preference. Preserve mandatory filters, explicit default eligibility, evidence coverage and an honest no-recommendation/insufficient-cost-data state. The reference-workload approach and cost/quality comparison are confirmed below; exact provider billing transformations, default numeric quality thresholds and deterministic tie handling remain to be specified.
- Cost modelling requirement from question 6: do not compare providers using a single advertised token price or an unsupported fixed cost per task. Represent ordinary input, generated output, cache reads and cache writes/creation (including distinct billing tiers where relevant) according to each provider's actual billing semantics. Avoid double-counting cached tokens already included in input totals; separately billed reasoning tokens or request fees must be represented when applicable. Missing rates or ambiguous billing semantics remain unknown, not zero.
- Confirmed question 6: provide reusable, editable Token Usage Profiles in global Settings. Allow selection of a project default and per-agent inheritance or override. Profiles describe reference workloads using absolute token counts or equivalent explicit ratios, including no-cache and cache-heavy scenarios; allow users to create and edit profiles. Example presets are illustrative assumptions, not measured usage. Persist effective profile values and reference volume with each evaluation for reproducibility; changing a profile recalculates costs without repeating benchmark analysis or changing quality scores. Compare routes under the same declared reference workload, not as a prediction of identical real token consumption across models. User-supplied usage data and future measured task usage may refine these profiles. Document assumptions and distinguish estimated costs from observed costs. Never infer universal input/output/cache ratios without evidence.
- Confirmed extension to question 6: support configurable token optimization in Token Usage Profiles, including a manually recorded RTK (Rust Token Killer) state (active, inactive, unknown) or other optimization tools. Distinguish measured post-optimization usage from estimated baseline usage. For estimates, allow explicit assumptions about the optimizable input share and reduction; apply reductions only to the relevant token categories, never to total cost or all tokens indiscriminately. Do not subtract estimated savings again from already optimized usage. Unknown savings remain unknown. Keep the assumptions, effective token counts and provenance with each evaluation; quality scores are unaffected by the cost calculation.
- Automatic RTK detection, import of RTK statistics and reconciliation with actual LLM billing/usage are post-MVP enhancements. No automatic modification of RTK or CLI configuration, and no assumption that RTK-reported token savings equal billed cost savings.
- Confirmed question 6: use reference-workload cost estimates as the basis for option C (least-cost eligible route satisfying quality requirements) and option D (Pareto comparison of quality and comparable costs). Do not claim equal actual token consumption or guaranteed cost per successful task. Show assumptions and unknown rates; do not rank incomparable cost categories as if equivalent. Question 7 confirms the common hosted token reference-cost model; local execution support and subscription allowance optimization are deferred. Question 8 confirms a per-agent selectable quality requirement: an absolute minimum normalized aggregate score, or a maximum permitted score-point gap from the highest-quality candidate eligible for standard recommendation. Allow an optional absolute floor with the relative strategy to avoid recommending weak models merely because the candidate set is weak. Determine the relative reference from the full comparable eligible candidate set after mandatory benchmark, evidence, route and default-eligibility checks, not from comparison-only candidates or the displayed top N. Select the least-cost qualifying route with comparable reference-cost evidence; show Pareto alternatives and explain unknown or incomparable costs, without silently relaxing requirements or claiming a guaranteed cheapest actual bill. Keep quality ranking independent. No numeric default thresholds have been approved. Preserve the unchanged quality ranking and apply mandatory filters and default eligibility to concrete routes before recommending them.
- Optional small practical prompt tests and judging (#2) are an early MVP enhancement, not a prerequisite for deterministic ranking and not evidence of privacy compliance. Actual task/rework cost optimization and large test suites remain future.

## Presentation and validation

- Label every value with currency, reference volume, profile and price source/date; differentiate route tariff, mapped proxy price and user estimate. If rates are missing for nonzero usage, show unknown (unless documented billing makes a category inapplicable). Never treat reference prices as subscription charges, actual savings or quota consumption. A genuinely free route requires verified evidence; a subscription is not inherently free.
- Validate cache accounting, separately billed reasoning, currency conversion and tiered/context pricing against documented billing semantics before adapter implementation. Preserve RTK assumptions and avoid applying reductions to measured optimized usage. Compare only compatible workloads and prices; when qualifying routes have unknown costs, clearly limit recommendation to comparable known estimates.
